# Coverage and CRAP for dashboard-core

`crates/quality` measures every production function in `dashboard-core`: its cyclomatic complexity, how many of its
lines the core tests run, and its CRAP score. It fails when coverage falls below the baseline or a function's CRAP gets
worse (#100). It isn't shipped; it only reads the source and a coverage report.

## Run it

```sh
rustup component add llvm-tools-preview
cargo install cargo-llvm-cov --version 0.9.1 --locked
cargo llvm-cov -p dashboard-core --locked --lcov --output-path target/quality/core.lcov
cargo run -p quality --locked -- crap --src crates/dashboard-core/src --lcov target/quality/core.lcov \
  --platform linux --revision "$(git rev-parse HEAD)" --baseline crates/quality/baselines/crap-linux.json \
  --out target/quality
```

Use `--platform windows` and `crap-windows.json` on Windows. The command writes `crap-<platform>.json` (every function,
with its lines, complexity, coverage, CRAP or exclusion reason) and `crap-<platform>.md` (totals, failures, review queue
and the 25 worst), and prints the Markdown. It exits 0 when the gate passes, 1 when it fails, and 2 when an input is
missing or malformed. A missing or unreadable baseline is an error, never a pass.

CI runs it in the required `core (ubuntu-latest)` and `core (windows-latest)` jobs. Pull requests run it at review,
and the push to `main` runs it again for the merged revision. Each job uploads `core-crap-<os>-<head sha>` with the
LCOV file and both reports. The report's `revision` is the commit the job checked out and measured.

## What is measured

- **Functions.** The walk starts at `src/lib.rs` and follows `mod` declarations, so it lists every free function,
  method, trait default method and nested `fn`, including those no test runs. A function with no instrumented line
  that ran scores 0% coverage. Test code is left out: `#[test]` functions, and anything under a `cfg` that only
  `cfg(test)` makes true, such as `mod tests` and `config_atomic_73.rs`. Functions generated by `macro_rules!` aren't
  listed.
- **Platforms.** Coverage is measured separately on Linux and Windows, each against its own baseline. A function the
  platform doesn't build is reported as excluded with its `cfg`, never as uncovered. On Linux that is the Windows ACL
  code in `config.rs` and `write.rs` (14 functions at the baseline); on Windows it is the Linux mode-bits code (7).
  Each is measured on the other platform. `owner_only_file` under `cfg(not(any(unix, windows)))` is built on
  neither and stays excluded on both. A `cfg` reaches everything under it: a file's `#![cfg(...)]`, a module's,
  and a function's nested `fn`s. `#[path]` modules are followed from the declaring file's folder. An unknown `cfg`
  predicate, or a `#[path]` inside an inline `mod` block, stops the run instead of guessing.
- **Coverage basis.** Lines, from LLVM source-based coverage on the stable toolchain: a function's coverage is the
  share of its own instrumented lines that ran at least once. Branch coverage needs a nightly compiler, so it isn't
  collected; #110 tracks adding it. A line holding both arms of an `if` counts as covered when either runs.
- **Complexity.** 1, plus one for each `if`, `while`, `for`, `?`, `let ... else`, `&&`, `||`, match guard and match
  arm after the first. Closures count toward the function that holds them. A nested `fn` is its own function.
- **CRAP** = complexity² × (1 − coverage)³ + complexity, with coverage from 0 to 1. A fully covered function scores its
  complexity; an unrun one scores complexity² + complexity.
- **Not measured.** `dashboard-app` (the GPUI views) isn't covered by this report. Its headless UI tests run in
  `cargo test --workspace`, but their coverage isn't collected or gated.

## The gate

From the baseline in `crates/quality/baselines/crap-<platform>.json`:

1. Line coverage over the measured functions must not fall below `line_coverage_floor`: the baseline's coverage
   rounded down to a tenth of a percent.
2. A function above CRAP 30 fails unless the baseline already had it above 30 and its score hasn't risen. That
   covers new functions above 30, existing ones crossing 30, and legacy ones getting worse.
3. Functions from 15 to 30 are listed as the review queue. They don't fail.

The first baselines were measured at `ee4c98d` (Linux on Ubuntu, Windows on Windows 11, both rustc 1.99.0 and
cargo-llvm-cov 0.9.1):

| Platform | Functions | Measured | Excluded | Line coverage | Floor | Legacy above 30 | Review queue |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Linux | 372 | 358 | 14 | 90.53% (3631 of 4011) | 90.5% | 8 | 16 |
| Windows | 372 | 365 | 7 | 90.75% (3739 of 4120) | 90.7% | 8 | 16 |

Two Windows runs gave identical per-function results. `dashboard-core` is unchanged from `ee4c98d` to this branch's base.

The legacy functions above 30, at the baseline, are `Kind::label` (272, run only by the app), `SortColumn::column`
(90), `status_label` (56), `Client::send` (44.99), `<WriteError as Display>::fmt` (37.43), `ColumnWidths::get`
(35.91), `checkout_identity` (33.74) and `backlog::rows` (33.03). Each may only improve.

## Updating a baseline

Run the command with `--write-baseline` on the platform in question; it rewrites the baseline from that measurement.
Do it in the pull request that changes the numbers, so the diff shows each moved score:

- after coverage rises, to raise the floor;
- when a function above 30 improves, to lock in its lower score;
- when a function is renamed or moved, since its key (`file::module::Type::name`) changes and the old score would
  otherwise read as a new function.

Lowering the floor, or accepting a higher score for a function above 30, needs its reason in the pull request
description. CI reports belong to whoever changed the code they measure: a failing gate is that pull request's to fix.
